# AI evaluation and operational limits

Run `npm run evaluate` if configured, or `node --import tsx evaluations/run.ts` from the repository root. The runner writes `evaluations/results-local.json`. It performs no network calls and incurs no model cost. The checked-in result is measured on the 18 handcrafted examples in `classification-v1.json`: accuracy 0.7222, macro-F1 0.7576. These are development smoke measurements, not a representative production benchmark. The deliberately varied paraphrases expose the keyword classifier's limits. Do not tune every rule to this tiny test set and then claim held-out performance.

`AI_PROVIDER=disabled` is the default. `AI_PROVIDER=local` enables a deterministic keyword classifier and lexical passage retriever. This is an extractive baseline, **not an LLM or semantic embedding system**. It returns source text verbatim for human review and abstains when retrieval finds nothing. It cannot reliably identify contradictions, policy exceptions, nuanced urgency, or paraphrases.

`AI_PROVIDER=openai`, `OPENAI_API_KEY`, and `AI_MODEL` enable the OpenAI Chat Completions adapter. This uses the same lexical retrieval baseline. Structured JSON is validated server-side and citation IDs must belong to the retrieved allowlist. No approved citation means the response is replaced with an abstention. The adapter performs at most two attempts with a 12-second per-attempt timeout; it retries one network failure or HTTP 429/5xx response. Invalid output fails safely. Human approval is still necessary: allowed citation IDs do not prove semantic groundedness or correctness of the generated prose. No response is sent by this module.

Provider usage tokens are returned when supplied. Set `AI_INPUT_USD_PER_MILLION` and `AI_OUTPUT_USD_PER_MILLION` using the actual model billing rates to obtain an estimated token cost; missing rates mean no cost estimate. Do not interpret local baseline latency as remote provider latency. Model names, credentials, prices, and rate limits need deployment-specific configuration.

The adapter redacts common email/phone patterns from ticket text before remote calls. This is a narrow minimization measure, not comprehensive PII detection. Policies and conversations may contain names, addresses, financial or medical data. Obtain an appropriate data-processing basis and implement organization-specific redaction/retention controls before using sensitive real customer data with a remote provider.

Prompt-injection defenses include marking supplied passages and messages as untrusted, no model tools or automatic sending, obvious-pattern exclusion in retrieval, schema validation, citation validation, and human review. Pattern filtering is incomplete and may reject legitimate text. The evaluation currently checks only one obvious malicious pattern. Expand with indirect attacks, policy contradictions, hidden instructions, multilingual examples, and adversarial source updates before enabling real use.

The caller must scope all supplied documents, tickets, history, and settings to the authorized tenant. The module has no database access and cannot independently prove tenant isolation. Its allowlist test only detects invented citation IDs. Database/API integration tests must verify actual cross-tenant access denial.

Before stronger release claims: add semantic embeddings with a tenant-filtered persistent vector index, a representative held-out customer dataset, relevance labels, human-reviewed groundedness judgments, provider outage/latency/cost testing, organization-aware quotas, and production monitoring. The current suite mocks the remote provider contract; it is not a live OpenAI integration verification.
